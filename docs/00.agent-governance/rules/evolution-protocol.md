# Evolution Protocol: AI-Driven Improvements

This protocol defines how the `Project-Template` evolves using automated insights from the Intelligence Hub.

## 1. Triggering Evolution
- Any agent or user can create a Stage 05 plan to propose governance or architecture evolution.
- Evolution proposals must be documented in canonical docs, not generated by missing local tooling.

## 2. Review & Approval
- **Proposal Assessment**: The human User or a Senior Architect agent must review `PROPOSAL.md`.
- **Decision Logic**:
    - **Accept**: Create a new Stage 05 plan in `docs/04.execution/plans/` based on the proposal.
    - **Defer**: Move the proposal to `docs/02.architecture/decisions/` as a "Pending Decision".
    - **Reject**: Delete the proposal and record the reasoning in `docs/00.agent-governance/policy-change-log.md` if it conflicts with core rules.

## 3. Implementation Gate
- No cross-layer refactoring can be executed without a corresponding `Stage 04 Spec` and `Stage 05 Plan` if it impacts cross-layer dependencies.
- Atomic changes (pruning single orphan files) can be executed directly as `Stage 06 Tasks`.

## 4. Feedback Loop
- If validation or repository intelligence produces a false positive, update the owning validation rule or script with a linked Stage 05 plan.
## Role definition

- Applies to autonomous workspace evolution proposals and architecture-debt remediation.

## Procedure

- Follow the trigger, review, implementation gate, and feedback loop defined above.
- Route accepted evolution work into canonical SDLC artifacts before execution.

## Constraints

- Do not execute cross-layer refactors without Stage 04 and Stage 05 anchors.
- Do not keep rejected proposals without recording the decision when they conflict with core rules.
